# 1. 專案概述

## 1.1 專案目標

建立一款 Android App，讓使用者可以集中管理個人筆記與待辦事項，並透過系統通知接收提醒。資料預設儲存在本機，使用者登入 Google 帳號後，可以將資料備份至自己的 Google Drive，並在其他裝置或重新安裝 App 後還原資料。

本產品採用離線優先架構，避免因網路不穩、雲端服務暫時不可用或使用者未登入，而無法新增及管理資料。

## 1.2 核心設計原則

1. **本機優先：** 筆記及待辦操作不依賴網路。
2. **資料安全：** 同步失敗不得直接覆蓋或刪除尚未同步的本機資料。
3. **提醒可靠：** 支援到期提醒與循環提醒。同一筆提醒不會重複通知。
4. **跨裝置還原：** 透過 Google Drive 備份與同步使用者資料。
5. **介面一致：** 字體大小設定應套用至所有主要畫面。
6. **狀態可追蹤：** 使用者可以查看雲端同步狀態及最後同步時間。

## 1.3 第一版功能範圍

| 模組 | 第一版內容 |
|---|---|
| 筆記 | 新增、列表、檢視、編輯、刪除 |
| 待辦 | 新增、編輯、完成、隱藏、刪除 |
| 提醒 | 到期提醒（單次日期與時間）、循環提醒（每隔 N 天） |
| 通知 | 每筆提醒各自顯示一則系統通知 |
| Google 帳號 | 登入、登出、重新登入 |
| Google Drive | 手動備份、還原、同步、同步狀態 |
| 個人化設定 | 字體大小 |
| 資料保存 | Room 本機資料庫 |
| 錯誤處理 | 網路中斷、權限不足、同步失敗、資料衝突 |

## 1.4 第一版不包含的功能

除非後續追加需求，第一版不實作：

- 多人共享筆記或共同待辦清單。
- 即時協作及即時推播同步。
- 圖片、錄音、附件及手寫筆記。
- 完整行事曆整合。
- 電子郵件、簡訊或第三方通訊軟體提醒。
- 多帳號資料合併。
- 付費訂閱及廣告。
- 每天、每週指定星期、每月指定日期。
- 把相同時間的多筆提醒合併成一則通知。

# 2. 使用者流程與畫面規劃

## 2.1 主導覽

底部導覽列包含三個主要分頁：

1. 待辦事項
2. 筆記
3. 設定

App 啟動後預設進入待辦事項頁面。

## 2.2 待辦事項頁面

依下列分類呈現資料：

- **今天：** 下次提醒在今天或更早、尚未完成的事項。
- **即將提醒：** 下次提醒在今天之後的未完成事項。
- **未設定提醒：** 沒有設定提醒的事項。
- **已完成：** 使用者已勾選完成的事項。

隱藏事項預設不出現在一般分類中，可透過「已隱藏」管理入口檢視及恢復。

分類規則：

1. 每個待辦事項只出現在一個主要分類。
2. 提醒時間已過但尚未完成的事項，歸入「今天」，並標示已過提醒時間。
3. 已完成事項歸入「已完成」，不因原提醒時間而重新出現在未完成列表。
4. 已隱藏或已刪除事項不出現在一般列表。
5. 循環提醒依下一次提醒時間分類。完成後不再通知；取消完成時，若下次時間已過，略過錯過的次數，只排定下一個未來時間。

## 2.3 筆記頁面

畫面包含：

- 筆記列表。
- 新增筆記按鈕。
- 筆記標題。
- 內容摘要。
- 最後修改時間。
- 編輯及刪除操作。

筆記編輯頁面包含標題欄位、內容編輯區及儲存狀態。

儲存方式建議採用自動儲存，並在資料成功寫入 Room 後顯示已儲存狀態。不得只在使用者離開畫面時才保存資料。

## 2.4 設定頁面

設定頁面包含：

- Google 帳號登入／登出。
- 目前登入帳號。
- Google Drive 備份。
- 還原資料。
- 手動同步。
- 最後同步時間。
- 同步錯誤提示。
- 字體大小設定。
- 提醒與通知權限狀態。
- 精確鬧鐘權限狀態。

# 3. 功能需求規格（PRD）

## 3.1 筆記功能

### FR-NOTE-001：新增筆記

使用者可以新增多筆筆記。

必要欄位：

- 標題。
- 內容。

規則：

- 標題與內容是否允許空白，應由產品規則統一決定；建議至少一項有實際內容才允許建立。
- 新增成功後，資料立即寫入 Room。
- 系統產生唯一筆記 ID。
- 自動記錄建立時間及最後修改時間。

### FR-NOTE-002：筆記列表

- 顯示所有未刪除筆記。
- 依最後修改時間由新至舊排序。
- 顯示標題、內容摘要及修改時間。
- 點選項目進入編輯頁面。
- 無資料時顯示空狀態及新增按鈕。

### FR-NOTE-003：編輯筆記

- 使用者可修改標題與內容。
- 修改成功後更新 `updatedAt`。
- 儲存至本機成功後，將資料標記為待同步。
- 若雲端同步失敗，仍保留本機修改。

### FR-NOTE-004：刪除筆記

- 刪除前顯示確認對話框。
- 刪除後立即從一般列表移除。
- 雲端同步需求下，優先使用軟刪除，保留刪除標記供其他裝置同步。
- 軟刪除資料不得被一般還原流程誤判為新增資料。

## 3.2 待辦事項功能

### FR-TASK-001：新增待辦事項

必要欄位：

- 事項名稱。

選填欄位：

- 說明。
- 提醒設定。可不設定。

提醒設定點選後只有兩個選項：

1. **到期提醒：** 選擇特定日期與時間，只提醒一次。
2. **循環提醒：** 輸入間隔天數。數字表示每隔幾天提醒一次，範圍為 1 到 365。並指定本地提醒時間，預設 09:00。若今天該時間尚未到，第一次為今天；否則為間隔天數之後的同一時間。通知送出後，下一次為本次時間加 N 天。

每筆待辦事項必須具有唯一 ID，且新增完成後立即寫入 Room。

### FR-TASK-002：編輯待辦事項

允許修改：

- 名稱。
- 說明。
- 提醒設定。可改為到期提醒、循環提醒，或清除提醒。

修改或清除提醒後，必須取消舊排程。若仍有未來的提醒時間，再建立新排程。

### FR-TASK-003：完成事項

- 每筆事項可獨立勾選完成。
- 完成後更新完成狀態及完成時間。
- 已完成事項不再發送提醒，並取消已排定的鬧鐘。
- 循環提醒完成後，不再排下一次通知。
- 使用者取消完成狀態時，重新判斷是否需要建立提醒。到期提醒若時間已過，不再補發。循環提醒若下次時間已過，略過錯過的次數，只排定下一個未來時間。

### FR-TASK-004：隱藏事項

- 隱藏與刪除是不同操作。
- 隱藏事項仍保留在本機及雲端資料中。
- 隱藏事項不出現在一般待辦分類。
- 隱藏事項不再發送提醒。
- 使用者可以恢復隱藏事項，恢復後重新計算提醒排程。

### FR-TASK-005：刪除事項

- 使用者可永久刪除待辦事項。
- 為確保跨裝置同步，資料應先標記為刪除，待同步確認及保留期限完成後再實際清除。
- 刪除操作必須取消相關鬧鐘及通知。
- 若刪除發生在離線狀態，刪除標記必須保留至成功同步。

## 3.3 提醒與週期功能

### FR-REM-001：到期提醒

使用者選擇特定日期及時間。此提醒只通知一次。

當到達提醒時間：

1. 系統觸發提醒排程。
2. 檢查事項是否仍存在、未完成、未隱藏且提醒仍有效。
3. 顯示系統通知。通知標題為事項名稱。
4. 該次提醒不再排程，避免重複通知。

若選擇的時間已過，不得排程，也不得補發通知。列表仍可依規則顯示已過提醒時間。

### FR-REM-002：循環提醒

使用者輸入間隔天數 N，並指定本地提醒時間。

規則：

- N 必須是 1 到 365 的整數。
- 預設提醒時間為 09:00，使用者可以修改。
- 若今天的提醒時間尚未到，第一次為今天該時間；否則為今天起算 N 天後的同一時間。
- 通知送出後，下一次為本次本地時間加 N 天，並重新排程。
- 裝置錯過多次時，不補發歷史通知，只排定下一個未來時間。
- 完成、隱藏或刪除後取消排程。
- 下一次時間的計算集中在 `ReminderSchedule`，不可散落在畫面中。

每天、每週指定星期、每月指定日期不在這一版。

### FR-REM-003：各自發送通知

這一版每筆有效提醒各自顯示一則系統通知，不依相同時間合併。

點擊通知後開啟 App。

同一筆提醒事件不得重複通知。修改提醒時間後，舊鬧鐘必須取消。

### FR-REM-006：相同時間合併通知（後續）

相同時間合併不在這一版。後續若要合併，規則如下：

當多個有效待辦事項的提醒時間相同時，合併成一則系統通知。

合併規則：

- 以實際提醒發生的時間點作為分組依據。
- 同一群組中的每筆事項仍保有獨立 ID、完成狀態及提醒規則。
- 通知標題顯示事項數量。
- 通知內容顯示部分事項名稱或摘要。
- 點擊通知後，進入對應的提醒事項清單。
- 同一群組再次處理時，不得重複發送已成功送出的通知。

通知群組 ID 應採用穩定且可重現的識別方式，避免每次排程時產生新的通知 ID，造成通知無法正確更新或取消。

若兩個提醒相差一分鐘，不視為同一時間，不合併。

### FR-REM-007：通知權限及排程恢復

- Android 13 以上應處理通知權限。
- Android 12 以上的精確鬧鐘需求，應處理相應的系統權限及可用性。
- 裝置重新開機後，重新讀取 Room 並恢復有效提醒。
- 使用者變更時區或系統時間後，重新計算相關排程。
- 權限遭撤銷時，應顯示提醒可能無法準時觸發的狀態。

## 3.4 Google 帳號及雲端功能

### FR-CLOUD-001：Google 登入

- 使用者主動點選登入按鈕後才啟動登入流程。
- 顯示目前登入的 Google 帳號。
- 登入成功後取得 Drive 存取授權。
- 登入驗證與 Drive API 授權應分開處理。
- 未取得 Drive 授權時，不得假設已具備雲端讀寫權限。

### FR-CLOUD-002：備份至 Google Drive

- 使用者可主動執行備份。
- 備份包含筆記、待辦事項、提醒規則及必要的使用者設定。
- 備份檔案應包含版本資訊及產生時間。
- 備份完成後顯示成功狀態。
- 失敗時保留本機資料，並顯示可理解的錯誤原因。
- 不得因備份失敗而清除待同步資料。

### FR-CLOUD-003：還原資料

- 首次登入或重新安裝後，使用者可以選擇還原雲端資料。
- 還原前顯示資料來源及本機資料處理方式。
- 若本機已有資料，不可直接覆蓋。
- 建議提供「合併資料」及「以雲端資料取代本機資料」兩種操作。
- 取代操作必須經使用者確認。
- 還原完成後重新建立有效的提醒排程。

### FR-CLOUD-004：手動同步

- 使用者可在設定頁面點選同步。
- 同步時顯示處理中狀態。
- 同步完成後更新最後同步時間。
- 同步失敗時保留待同步資料。
- 重複觸發同步時，應避免同時執行互相衝突的資料寫入流程。

### FR-CLOUD-005：登出

- 登出只解除帳號關聯及必要的授權狀態。
- 預設保留本機資料。
- 登出後停止對該帳號執行雲端同步。
- 不得因登出而自動刪除 Google Drive 上的備份。
- 重新登入其他帳號前，應提示帳號切換及資料隔離風險。

## 3.5 字體大小設定

### FR-SETTING-001：字體大小

第一版提供：

- 小。
- 中。
- 大。

建議預設為中。

設定值使用 DataStore 保存，並立即套用於筆記列表、筆記編輯頁、待辦列表、對話框及設定頁。

不得只修改首頁文字大小。所有主要畫面應使用統一的字體尺寸管理機制。

## 4.4 資料存取規則

所有主要資料讀寫應透過 Repository。

UI 不得直接存取 DAO 或 Google Drive API。

資料修改流程：

1. 使用者操作 UI。
2. ViewModel 呼叫 UseCase。
3. UseCase 驗證資料及執行業務規則。
4. Repository 將資料寫入 Room。
5. Room 更新後，UI 透過 Flow 接收新狀態。
6. 同步佇列記錄需要上傳的資料。
7. WorkManager 在適當時機執行雲端同步。

本機資料成功寫入後，即使雲端不可用，也必須視為使用者操作成功。

# 5. 資料庫規格

所有時間欄位建議統一使用 UTC epoch milliseconds 儲存。循環提醒的下一次時間以本地日期與時間計算後，再存成 UTC epoch milliseconds。

## 5.1 NoteEntity

| 欄位 | 型別 | 說明 |
|---|---|---|
| id | String | UUID 主鍵 |
| title | String | 筆記標題 |
| content | String | 筆記內容 |
| createdAt | Long | 建立時間 |
| updatedAt | Long | 最後修改時間 |
| deletedAt | Long? | 軟刪除時間 |
| revision | Long | 本機資料版本 |
| syncStatus | String | PENDING / SYNCED / ERROR |

## 5.2 TaskEntity

| 欄位 | 型別 | 說明 |
|---|---|---|
| id | String | UUID 主鍵 |
| title | String | 事項名稱 |
| description | String? | 事項說明 |
| reminderType | String | NONE / ONCE / INTERVAL |
| reminderAt | Long? | 下一次或單次提醒時間 |
| intervalDays | Int? | 循環提醒的間隔天數；NONE 與 ONCE 為空 |
| isCompleted | Boolean | 是否完成 |
| completedAt | Long? | 完成時間 |
| isHidden | Boolean | 是否隱藏 |
| createdAt | Long | 建立時間 |
| updatedAt | Long | 最後修改時間 |
| deletedAt | Long? | 軟刪除時間 |
| revision | Long | 本機資料版本 |
| syncStatus | String | 同步狀態 |

## 5.3 ReminderEntity（後續）

第一版不建立此表。提醒設定直接存在 `TaskEntity`。下列獨立資料表留待每天、每週、每月等規則再拆出。

| 欄位 | 型別 | 說明 |
|---|---|---|
| id | String | UUID 主鍵 |
| taskId | String | 關聯 TaskEntity |
| reminderType | String | ONCE / DAILY / WEEKLY / MONTHLY / CUSTOM |
| triggerAt | Long? | 單次提醒時間 |
| localTime | String? | 本地時間，例如 20:00 |
| timeZoneId | String | IANA 時區 ID |
| repeatRule | String? | 週期規則 JSON |
| startDate | String? | 週期起始日期 |
| endDate | String? | 週期結束日期 |
| isEnabled | Boolean | 是否啟用 |
| updatedAt | Long | 最後修改時間 |
| deletedAt | Long? | 軟刪除時間 |

週期規則範例保留於後續版本。星期編碼必須統一，建議使用 ISO-8601：星期一為 1，星期日為 7。

`repeatRule` 應由專用資料類別進行序列化及驗證，不得直接在 UI 中拼接 JSON 字串。

## 5.4 ReminderOccurrenceEntity

為了追蹤每次週期提醒是否已完成及是否已發送通知，建議增加提醒發生紀錄表。

| 欄位 | 型別 | 說明 |
|---|---|---|
| id | String | 唯一識別碼 |
| reminderId | String | 提醒規則 ID |
| occurrenceKey | String | 當期唯一識別碼 |
| scheduledAt | Long | 預定提醒時間 |
| status | String | PENDING / COMPLETED / SKIPPED |
| notificationSentAt | Long? | 通知發送時間 |
| createdAt | Long | 建立時間 |

建議建立唯一索引：

`UNIQUE(reminderId, occurrenceKey)`

此設計可避免 App 重啟、重複排程或重新同步時，建立重複的當期提醒紀錄。

## 5.5 SyncOperationEntity

同步佇列用來記錄尚未完成的雲端操作。

| 欄位 | 型別 | 說明 |
|---|---|---|
| id | String | 操作 ID |
| entityType | String | NOTE / TASK / REMINDER |
| entityId | String | 對應資料 ID |
| operation | String | UPSERT / DELETE |
| payloadVersion | Long | 送出時的資料版本 |
| retryCount | Int | 重試次數 |
| createdAt | Long | 建立時間 |
| lastError | String? | 最近一次錯誤 |

同一筆資料如果在同步前被多次修改，可以合併成最新的 UPSERT 操作；但 DELETE 必須保留，直到確認雲端及同步規則均已處理。

## 5.6 資料庫索引與完整性

建議索引：

- `NoteEntity.updatedAt`
- `TaskEntity.reminderAt`
- `TaskEntity.isCompleted`
- `TaskEntity.isHidden`
- `ReminderEntity.taskId`
- `ReminderOccurrenceEntity.scheduledAt`
- `SyncOperationEntity.createdAt`

`ReminderEntity.taskId` 應具有明確的關聯完整性策略。刪除待辦時，必須同步停用相關提醒及排程，避免留下孤兒資料。

# 6. Google Drive 雲端設計

## 6.1 儲存方式

採用使用者可見的 Google Drive 檔案。

建議建立專屬資料夾，例如：

`MyNotesBackup/`

資料夾內至少包含：

- `manifest.json`：備份版本、時間及檔案資訊。
- `data.json`：筆記、待辦、提醒及必要的偏好資料。

後續若備份資料量增加，可改為分檔或資料分區。

Google Drive 的資料夾及檔案應透過 API 建立並保存其 file ID，不得每次同步都以檔名重新搜尋後直接建立新檔案，否則容易產生重複備份。

## 6.2 備份格式

正式備份為 JSON，包含 schemaVersion、backupId、createdAt、appVersion，以及 notes、tasks、reminders、occurrences。

正式實作應確認：

- JSON 欄位版本。
- 必要欄位與預設值。
- 備份檔案大小限制。
- 資料驗證。
- 不支援版本的處理方式。
- 匯入失敗時的復原機制。

## 6.3 同步策略

採用「本機優先、增量同步、明確衝突處理」。

### 同步流程

1. 確認 Google 帳號及 Drive 授權有效。
2. 從 Room 讀取待同步操作。
3. 讀取雲端 manifest 及對應資料。
4. 比對資料 ID、版本、修改時間及刪除標記。
5. 判斷新增、更新、刪除及衝突。
6. 上傳或下載必要資料。
7. 確認雲端寫入成功。
8. 更新本機同步狀態。
9. 清除已完成的同步操作。
10. 更新最後同步時間。

任何步驟失敗時，不得將未確認成功的資料標記為已同步。

### 衝突處理

若同一筆資料在不同裝置被修改：

- 先比對唯一 ID。
- 比對修改時間及資料版本。
- 若能明確判定先後，依版本規則處理。
- 若雙方都有未同步修改且無法安全判定，保留兩份候選資料或產生衝突紀錄，避免直接丟棄內容。

僅依 `updatedAt` 判斷最後寫入者勝出，不能完全解決跨裝置時鐘偏差問題。

### 刪除同步

刪除採軟刪除及 tombstone（刪除標記）。

只有在確認相關裝置已同步刪除，或經過明確定義的資料保留期限後，才可永久清除刪除標記。若沒有伺服器或裝置同步確認機制，不得假設所有裝置都已收到刪除操作。

## 6.4 Google 授權與安全性

- 登入與 Drive API 授權分開處理。
- 只要求必要的 Google Drive 權限。
- 優先評估 `drive.file` 等限制範圍的授權方式。
- 使用者需理解 App 會在 Google Drive 建立及更新備份檔案。
- 不在 Logcat、分析事件或錯誤訊息中輸出筆記正文、帳號憑證或存取 Token。
- 登出時清理本機保存的授權狀態。
- 備份資料如包含敏感內容，應評估檔案加密及金鑰管理方案。

如果採用 `drive.file`，必須確認 App 建立的備份檔案能在重新登入、重新授權及重新安裝情境下被正確尋回。不得只依賴檔名判斷檔案所有權。

# 7. 提醒排程與通知設計

## 7.1 排程策略

建議由 `ReminderScheduler` 統一管理所有鬧鐘。

- 到期提醒：使用 `AlarmManager`，只排一次。
- 循環提醒：由 `ReminderSchedule` 計算下一次時間，通知送出後再排下一次，不使用無限重複的系統鬧鐘。
- 雲端同步：使用 `WorkManager`。
- 通知發送：由 `BroadcastReceiver` 接收鬧鐘事件，讀取 Room 並建立通知。

不要將每個週期提醒永久轉成無限重複的系統鬧鐘。使用資料庫保存週期規則，並計算下一次有效提醒，較容易處理完成狀態、修改規則及跨時區問題。

## 7.2 排程唯一識別

每個提醒事件需具有穩定的識別碼。

建議以 `reminderId + occurrenceKey` 形成唯一邏輯識別，並轉換成穩定的 `PendingIntent` request code 或其他可識別的排程鍵值。

修改提醒時：

1. 取消舊排程。
2. 更新資料庫。
3. 計算下一次有效提醒。
4. 建立新排程。

刪除或隱藏事項時，應取消所有相關排程及通知。

## 7.3 相同時間的合併處理（後續）

這一版不合併通知。後續若實作合併，通知事件發生時，系統應在資料庫交易或一致性處理流程中確認：

- 該事項仍存在。
- 尚未完成。
- 未被隱藏。
- 提醒規則仍有效。
- 該期尚未發送通知。

接著依相同的 `scheduledAt` 分組，將同一時段所有有效事項整合為一則通知。

若多個鬧鐘在極短時間內先後觸發，應透過共用的通知群組及去重機制，避免分別發出多則通知。

通知內容可能因 Android 版本或鎖定畫面隱私設定而被截斷，因此必須提供穩定的通知標題、數量摘要及點擊入口。

## 7.4 權限與系統限制

- Android 13 以上需處理 `POST_NOTIFICATIONS` 通知權限。
- Android 12 以上需評估精確鬧鐘權限。
- `SCHEDULE_EXACT_ALARM` 是否可使用，應透過系統 API 確認。
- 不可假設所有裝置都允許精確鬧鐘。
- 權限未授予時，應清楚提示使用者，並依產品政策降級為非精確提醒或顯示提醒受限狀態。
- 不得將 `WorkManager` 當成精確到分鐘的鬧鐘替代品。

## 7.5 裝置重新開機及時間變更

在適當的系統事件發生時，重新讀取 Room 並重建排程，包括：

- 裝置重新開機。
- 使用者變更系統時間。
- 使用者變更時區。
- 精確鬧鐘權限恢復。
- App 更新後需要重新建立排程。

排程重建必須具備冪等性，即相同資料重複執行重建流程，不會建立重複鬧鐘。

# 8. 錯誤處理規格

| 情境 | 預期處理 |
|---|---|
| 新增資料時 App 關閉 | 以已寫入 Room 的資料為準 |
| Google 登入失敗 | 顯示原因，可重新登入 |
| Drive 權限遭撤銷 | 停止雲端操作，保留本機資料 |
| 網路中斷 | 保存本機修改，保留待同步佇列 |
| 雲端上傳失敗 | 不標記為已同步，允許重試 |
| 下載備份格式錯誤 | 中止匯入，不覆蓋現有資料 |
| 還原時遇到重複 ID | 依合併規則處理，不重複建立 |
| 同步發生資料衝突 | 保留衝突資料並記錄處理結果 |
| 通知權限被拒絕 | 顯示通知受限狀態及設定入口 |
| 精確鬧鐘權限不足 | 顯示受限狀態，依規則降級 |
| 裝置重新開機 | 重新計算有效排程 |
| 使用者切換 Google 帳號 | 提示資料來源及帳號切換風險 |
| Room 資料庫升級 | 執行版本遷移，不得直接清除資料 |

錯誤訊息應區分使用者可處理的問題與系統內部錯誤。對外訊息不得暴露 Token、完整備份內容或不必要的內部例外堆疊。

# 9. UI 狀態與操作規範

## 9.1 狀態管理

每個主要功能使用獨立 ViewModel，避免將所有功能集中於單一 ViewModel。

建議：

- `TaskListViewModel`
- `TaskEditorViewModel`
- `NoteListViewModel`
- `NoteEditorViewModel`
- `SettingsViewModel`
- `SyncViewModel`

畫面狀態應明確區分：

- Loading：載入中。
- Content：正常顯示。
- Empty：沒有資料。
- Error：載入或操作失敗。
- Syncing：雲端同步中。
- Offline：目前無法連線。
- PermissionRequired：缺少必要權限。

## 9.2 UI 與資料一致性

1. 新增或修改資料時，先完成本機資料寫入。
2. 本機資料寫入成功後才顯示成功狀態。
3. 雲端同步不得阻塞一般筆記與待辦操作。
4. 畫面不得因重新進入分頁而重複新增資料。
5. 列表使用 Room Flow 更新，避免手動維護多份容易不一致的資料副本。

## 9.3 字體大小

建議建立統一的 `AppTypography` 或字體尺寸管理機制，提供小、中、大三組尺寸。

Compose 主要畫面應共用此設定。字體大小變更後，列表、編輯器、對話框及通知導向畫面都應保持可讀性。

# 13. 非功能性需求

## 13.1 效能

- 一般筆記及待辦操作不得等待雲端回應。
- 資料庫操作不得在主執行緒執行。
- 列表應支援足量資料的載入及更新。
- 同步工作不得長時間阻塞 UI。
- 排程及通知處理不得造成明顯的主執行緒卡頓。

## 13.2 可靠性

- 所有本機資料操作具備明確成功與失敗狀態。
- 重複執行同步及排程恢復應具備冪等性。
- 資料庫升級應提供 Migration。
- 雲端備份匯入應先驗證格式，再提交資料變更。
- 關鍵操作應有測試覆蓋。

## 13.3 安全性

- 不在 Logcat 輸出敏感內容。
- Google 存取權限遵循最小權限原則。
- 雲端備份及還原需驗證資料格式。
- 不支援的備份版本不得直接覆蓋現有資料。
- 評估備份檔案加密、金鑰保護及敏感資料保存政策。

## 13.4 可維護性

- 週期計算、同步衝突及提醒排程需獨立封裝。
- 時間計算應可注入測試時鐘。
- 資料庫操作透過 Repository 管理。
- 不可將商業邏輯散落在 Compose UI。
- 同步、提醒及資料庫流程均需有自動化測試。

# 14. 尚待確認的產品決策

以下項目在正式開發前應由產品負責人確認：

1. **最低 Android 版本：** 建議先評估 Android 10 以上，實際版本需依目標使用者決定。
2. **精確提醒：** 是否要求接近指定分鐘觸發，以及使用者拒絕精確鬧鐘權限時的降級行為。
3. **循環提醒完成規則：** 已決定。完成後取消後續通知；取消完成時，只排定下一個未來時間，不補發錯過的通知。
4. **循環提醒起算方式：** 已決定。若今天的指定時間尚未到，第一次為今天；否則為間隔天數之後的同一時間。之後每次加 N 天。
5. **同步頻率：** 只手動同步、App 開啟時同步，或加入背景同步。
6. **資料合併：** 還原時是否預設合併，或讓使用者選擇取代本機資料。
7. **備份保留：** Google Drive 僅保存最新備份，或保留多個歷史版本。
8. **刪除保留期限：** 軟刪除資料保留多久後才可永久清除。
9. **備份加密：** 是否需要使用者密碼或其他方式加密備份檔案。
10. **跨裝置支援：** 是否需要處理多台裝置同時編輯同一份資料的衝突。

上述項目若尚未確認，開發時應採用本文件已定義的預設規則，不得由各功能自行決定不同的處理方式。
